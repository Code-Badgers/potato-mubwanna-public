# Issue #410 Validation

## 작업 범위

- `gamjamubwanna_travel_course_content_plan.md`를 기준으로 지도 탭 Discovery 홈의 여행 코스 콘텐츠를 고도화했다.
- 기존 Kakao Map, 장소 상세, 내 동선 저장/조회/삭제, 북마크, 길찾기 로직은 재작성하지 않고 기존 `MapScreen` 상태와 provider 흐름을 재사용했다.
- 코스 데이터는 추후 API 교체가 쉽도록 `travel_course_catalog.dart`로 분리했다.

## 구현 내용

- 지도 홈의 코스 섹션을 `오늘 어떤 여행이 끌리나요? 🌿`로 변경했다.
- 기획 문서 기준 6개 코스를 추가했다.
  - 오늘 감자로 배 채워볼까? 🥔
  - 사람 구경도 여행이지! 👋
  - 강원도에서 요즘 제일 핫한 곳 🔥
  - 사람 많은 곳은 조금 힘들어요 🌿
  - 오늘은 바다만 보고 싶어 🌊
  - 그냥 찍어도 분위기 좋은 곳 📷
- 코스 상세를 블로그형 하단 시트로 구성했다.
- `내 동선에 N곳 담기`는 기존 즐겨찾기/동선 저장 로직을 반복 호출해 중복을 제외하고 추가한다.
- 코스 담기 완료 시 스낵바 대신 반투명 배경 모달을 표시하고, `지도에서 확인하기`를 누르면 기존 전체 지도 내 동선 모드로 진입한다.
- `요즘 많이 찾는 곳`은 임의 인기 표현을 피하고 `지금 가기 좋은 곳 ☀️`으로 변경했다.
- `지금 가기 좋은 곳 ☀️`은 한국관광공사 관광지 집중률 예측 데이터를 백엔드가 반영해 내려주는 `congestionLevel`을 기준으로 `내향인 전용 여유로운 장소`와 `외향인 전용 사람 좋아 핫플`로 분리했다.
- `오늘 어떤 여행이 끌리나요? 🌿` 우측의 `전체 보기` 버튼은 현재 동작이 없으므로 제거했다.

## PAR 기록

### Problem

- 기존 코스 카드는 기능형 카드에 가까워 사용자가 “오늘 어디를 갈지” 결정하는 콘텐츠 감성이 약했다.
- 코스를 동선에 담았을 때 단순 스낵바만 보여 사용자가 실제로 동선이 채워졌다는 보상을 느끼기 어려웠다.
- 테스트에서는 코스 카드가 화면 밖에 있어 바로 탭할 때 실패했다.

### Action

- 코스 콘텐츠를 별도 catalog 모델로 분리하고, 기존 `MapSpot` 데이터에서 장소를 매칭하도록 구성했다.
- 코스 상세에는 대표 이미지, 감성형 제목, 메타 정보, 장소별 설명, 담긴 장소 리스트, 동선 담기 CTA를 넣었다.
- 동선 담기 완료 UX는 첨부 레퍼런스처럼 어두운 scrim 위 중앙 모달로 바꿨고 감자 이미지는 넣지 않았다.
- 테스트는 실제 사용자 흐름처럼 Discovery 홈을 스크롤한 뒤 코스 카드를 열고, 동선 담기 모달과 내 동선 모드 전환을 검증하도록 보완했다.

### Result

- 지도 홈에서 코스 발견 → 코스 상세 확인 → 내 동선에 한 번에 담기 → 전체 지도 내 동선 확인 흐름이 자동 테스트로 검증됐다.
- 기존 지도 필터, 마커 선택, 북마크, 내 동선 순서 변경/삭제 테스트가 함께 통과했다.

### Problem

- `지금 가기 좋은 곳`이 단순 장소 목록으로만 보여서, 사용자가 “사람 많은 핫플을 갈지 / 조용한 곳을 갈지” 선택하기 어려웠다.
- 한국관광공사 집중률 API 인증키는 민감 설정이므로 프론트에 직접 넣으면 안 되고, 기존 백엔드 동기화 결과를 재사용해야 했다.

### Action

- 기존 `MapSpot.congestionLevel` 값을 재사용해 `LOW`는 여유로운 장소, `HIGH`는 핫플 그룹으로 노출했다.
- 데이터가 부족한 경우에는 `NORMAL`, 스탬프 가능 장소, 전체 장소 순서로 fallback해 빈 섹션이 생기지 않도록 했다.
- 실제 공공데이터 API key는 코드나 문서에 남기지 않고, 운영 환경 변수 `CONGESTION_API_SERVICE_KEY` 또는 `TOUR_API_SERVICE_KEY`로 주입되는 기존 백엔드 구조를 유지했다.

### Result

- 지도 홈에서 혼잡도 관점의 두 가지 선택지가 생겼고, 사용자는 조용한 여행/활기 있는 여행 중 원하는 톤으로 장소를 고를 수 있다.
- 프론트는 신규 외부 API 호출 없이 기존 백엔드 응답만 사용하므로 API key 노출 위험이 없다.
