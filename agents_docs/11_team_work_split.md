# 11. Team Work Split

이 문서는 MVP 구현을 두 명이 나누어 진행할 때의 역할 기준이다. 핵심 기능은 사용자, 지도, 랠리북, 감자, 미션 5개 축으로 나누고, 외부 공공 API 연동 책임까지 함께 정의한다.

## 1. 기능 축

현재 MVP의 주요 기능 축은 다음과 같다.

1. 사용자: 로그인 세션, 마이페이지, 내 정보, 보상함
2. 지도: 관광지 탐색, 카카오 지도 마커, 관광지 상세, 방문 인증
3. 랠리북: 스탬프 수집 현황, 지역별 진행률, 다음 보상
4. 감자: 감자 도감, 희귀도, 획득, 성장
5. 미션: 점순이 미션, 미션 완료, 미션 보상

부가 기능으로 온보딩, 접근권한 안내, 알림, SNS 공유, 관리자 기능, 운영 통계가 있을 수 있으나 MVP 개발 역할은 위 5개 축을 우선한다.

0.1 국문 관광정보: Team B 주 담당, Team A 랠리북 매핑 검수
0.2 오디오 가이드: Team A 주 담당, Team B 화면 연결
0.3 혼잡도/방문자 추이: Team B 주 담당, Team A 보상/이력 연결
0.4 연관 관광지: Team A 주 담당, Team B 지도 렌더링

## 2. Team A: 사용자 / 보상 / 랠리북

Team A는 사용자의 계정 상태, 수집 결과, 보상 확인 흐름을 담당한다.

### 2.1 사용자

#### Backend

- 카카오 로그인 이후 사용자 저장/조회 안정화
- access token, refresh token 세션 유지
- refresh token rotation
- 로그아웃, 탈퇴 또는 연결 해제 정책 준비
- 내 정보 조회 API 구현
- 사용자 활동 요약 API 구현

#### Frontend

- 로그인 상태 유지
- 마이페이지 화면 구현
- 닉네임, 이메일, 가입일, 수집률, 보상 개수 표시
- 로그아웃 버튼 구현
- 접근권한 설정 안내 영역 구현

#### API

```http
GET /api/users/user
PATCH /api/users/user
POST /api/auth/refresh
POST /api/auth/logout
```

### 2.2 보상

#### Backend

- 내 보상 목록 조회
- 보상 지급 이력 조회
- 쿠폰 상세 조회
- QR 쿠폰 조회
- 쿠폰 사용 처리 구조 준비
- 랠리북 또는 미션 완료 이벤트와 보상 지급 연결

#### Frontend

- 보상함 화면 구현
- 사용 가능 / 사용 완료 탭 구현
- QR 보기 화면 또는 모달 구현
- 쿠폰 이름, 금액, 유효기간, 사용 상태 표시

#### API

```http
GET /api/rewards/user
GET /api/rewards/{rewardId}
GET /api/coupons/user
GET /api/coupons/{couponId}/qr
POST /api/coupons/{couponId}/use
```

### 2.3 랠리북

#### Backend

- 내 스탬프 목록 조회
- 지역별 스탬프 획득 여부 조회
- 전체 수집률 계산
- 다음 보상 조건 조회
- 방문 인증 성공 이벤트와 스탬프 지급 연결

#### Frontend

- 랠리북 화면 구현
- `8 / 18` 형태의 수집률 표시
- 지역별 완료/미완료 상태 표시
- 다음 보상 카드 표시
- 스탬프 획득 후 랠리북 반영 상태 확인

#### API

```http
GET /api/stamps/user
GET /api/rallybook/user
GET /api/rallybook/rewards/next
```

### 2.4 Team A 완료 기준

- 로그인한 사용자가 본인 정보를 볼 수 있다.
- 사용자가 획득한 스탬프와 랠리북 진행률을 볼 수 있다.
- 사용자가 받을 수 있는 보상과 QR 쿠폰을 볼 수 있다.
- 보상 지급 조건이 백엔드에서 계산되고 프론트에 표시된다.

## 3. Team B: 지도 / 감자 / 미션

Team B는 사용자가 장소를 찾고, 방문 인증을 통해 감자와 미션 보상을 얻는 핵심 플레이 루프를 담당한다.

### 3.1 지도

#### Backend

- 관광지 스팟 목록 조회
- 관광지 카테고리 필터
- 관광지 상세 조회
- 좌표 기반 주변 스팟 조회
- 외부 관광 데이터 수집 결과를 프론트 지도 API로 제공

#### Frontend

- 카카오 지도 화면 구현
- 감자 마커 렌더링
- 카테고리 필터 구현
- 마커 클릭 시 바텀시트 표시
- 상세보기 이동
- 길찾기 버튼 구현

#### API

```http
GET /api/spots
GET /api/spots?category=TOUR
GET /api/spots/nearby?lat={lat}&lng={lng}
GET /api/spots/{spotId}
```

### 3.2 방문 인증

#### Backend

- 사용자 현재 위치와 스팟 좌표 거리 계산
- 방문 인증 성공/실패 처리
- 중복 방문 인증 방지
- 인증 성공 시 스탬프 지급 이벤트 발생
- 인증 성공 시 감자 획득 로직 실행
- 인증 성공 시 점순이 미션 또는 오디오 가이드 응답 연결

#### Frontend

- 관광지 상세 화면의 방문 인증 버튼 구현
- 위치 권한 요청 연결
- 인증 성공 화면 구현
- 스탬프 획득, 감자 획득, 다음 장소 추천 결과 표시

#### API

```http
POST /api/visits/verify
GET /api/visits/user
```

요청 예시:

```json
{
  "spotId": 1,
  "latitude": 37.3808,
  "longitude": 128.6609
}
```

### 3.3 감자 도감

#### Backend

- 감자 캐릭터 목록 조회
- 내 감자 목록 조회
- 감자 상세 조회
- 감자 희귀도 정책 구현
- 감자 성장 정보 저장
- 혼잡도 기반 희귀 감자 출현 확률 계산

#### Frontend

- 감자 도감 그리드 구현
- 획득 / 미획득 상태 표시
- 희귀도 표시: 일반 / 희귀 / 황금 / 전설
- 감자 상세 화면 구현
- 성장 레벨, 이동거리, 획득 지역 표시

#### API

```http
GET /api/potatoes
GET /api/potatoes/user
GET /api/potatoes/{potatoId}
POST /api/potatoes/{potatoId}/grow
```

### 3.4 점순이 미션

#### Backend

- 스팟별 미션 조회
- 내 미션 진행 상태 조회
- 미션 완료 처리
- 미션 완료 보상 지급
- 방문 인증 성공 이벤트와 미션 등장 조건 연결

#### Frontend

- 점순이 미션 등장 화면 구현
- 미션 상세 화면 구현
- 도전하기 버튼 구현
- 완료 결과 화면 구현
- 보상 획득 표시

#### API

```http

```

### 3.5 Team B 완료 기준

- 사용자가 지도에서 관광지 스팟을 볼 수 있다.
- 사용자가 스팟 상세에서 방문 인증을 시도할 수 있다.
- 방문 인증 성공 시 감자, 스탬프, 미션 흐름이 이어진다.
- 지도, 감자 도감, 미션 화면이 동일한 API 데이터 기준으로 동작한다.

## 4. External API Responsibility

외부 API는 관광 데이터 수집과 사용자 경험 강화에 사용한다. 외부 API 원본 응답을 프론트에 그대로 노출하지 않고, 백엔드에서 앱 도메인에 맞게 가공한 REST API를 제공한다.

외부 API 담당이 한 사람에게 몰리지 않도록 다음 기준으로 나눈다.

- Team B는 지도, 관광지 상세, 방문 인증, 감자 희귀도처럼 장소 기반 실시간 경험을 담당한다.
- Team A는 사용자 이력, 랠리북, 보상, 스탬프 획득 이후 결과 정리와 보상 연결을 담당한다.
- 외부 API 수집 파이프라인은 주 담당이 만들되, 응답 계약은 두 팀이 함께 검토한다.

| 번호 | 외부 API | 사용 기능 | 활용 목적 | Backend 책임 | Frontend 책임 | 주 담당 / 협업 |
| --- | --- | --- | --- | --- | --- | --- |
| 0.1 | 한국관광공사 국문 관광정보 서비스 | 지도, 관광지 상세, 방문 인증, 랠리북 | 감자 지도 데이터베이스 구축. 관광지, 음식점, 체험시설 정보를 가져와 감자 관련 태그를 붙인다. | Spring Batch 또는 Scheduler로 주 1회 데이터를 수집하고 `places` 또는 `spots` 테이블에 적재한다. 감자 태그, 카테고리, 지역 스탬프 매핑을 가공한다. | 백엔드 관광지 리스트 API를 받아 카카오 지도 위에 감자 마커로 렌더링한다. 관광지 상세와 랠리북 지역명도 같은 데이터 기준을 사용한다. | 주 담당: Team B. 협업: Team A는 지역 스탬프/랠리북 매핑 검수 |

| 0.3 | 한국관광공사 관광지 집중률 방문자 추이 예측 정보 | 지도, 관광지 상세, 방문 인증, 감자 도감, 보상 정책 | 혼잡도 표시와 희귀도 알고리즘. 사람이 적은 장소일수록 황금감자 또는 전설감자 출현 확률을 높인다. | 매시간 혼잡도 예측 데이터를 수집한다. 방문 인증 시 혼잡도 기반 희귀도 주사위 로직을 처리하고, 희귀 감자 획득 결과를 사용자 수집 이력과 보상 조건에 연결한다. | 지도/상세 화면에 혼잡도를 표시한다. 인증 결과 화면에서 획득 감자 연출을 표시하고, 감자 도감과 보상함에 반영된 상태를 보여준다. | 주 담당: Team B. 협업: Team A는 보상 조건/사용자 이력 연결 |
| 0.4 | 한국관광공사 관광지별 연관 관광지 정보 | 지도 추천 동선, 방문 인증 성공 결과, 랠리북 다음 목표 | 지도 탭의 추천 동선. 스탬프 획득 후 근처 다음 목적지 3곳 추천에 사용한다. | 현재 획득한 관광지 ID와 사용자의 랠리북 미완료 지역을 함께 고려해 추천 목적지 3곳을 생성한다. 추천 결과는 방문 인증 성공 응답과 랠리북 다음 목표 API에서 재사용한다. | 추천 장소 3곳을 지도 위에 표시하고 필요하면 카카오맵 Polyline으로 동선을 그린다. 랠리북에는 다음 목표 카드로 노출한다. | 주 담당: Team A. 협업: Team B는 지도 Polyline/마커 렌더링 |

## 5. Cross-Team Contract

두 팀이 충돌을 줄이기 위해 다음 계약을 먼저 맞춘다.

### 5.0 작업 선점과 충돌 방지

- 모든 작업은 GitHub Issue 하나에 연결한다.
- Issue에는 주 담당, 협업 담당, 작업 브랜치, 작업 범위, 제외 범위를 적는다.
- 같은 파일을 두 팀 또는 두 에이전트가 동시에 수정해야 하면 먼저 Issue나 PR에서 순서를 정한다.
- 공유 위험 파일은 수정 전 조율이 필요하다. 공유 위험 파일은 `agents_docs/**/*.md`, `.github/**`, `frontend/pubspec.yaml`, `backend/build.gradle`, `backend/src/main/resources/application.yml`, 라우터, 테마, 공통 네트워크/인증 코드, Flyway migration, 공통 DTO/API 응답이다.
- 공유 위험 파일을 수정한 PR은 리뷰 중점사항에 변경 이유와 영향 범위를 적는다.

### 5.1 공통 식별자

- 사용자 식별자: `userId`
- 관광지 식별자: `spotId`
- 스탬프 식별자: `stampId`
- 감자 식별자: `potatoId`
- 미션 식별자: `missionId`
- 보상 식별자: `rewardId`
- 쿠폰 식별자: `couponId`

### 5.2 이벤트 흐름

방문 인증 성공 시 다음 순서로 처리한다.

1. 방문 인증 성공 기록 생성
2. 스탬프 지급
3. 감자 획득 또는 성장 처리
4. 미션 등장 또는 완료 조건 확인
5. 보상 지급 조건 확인
6. 다음 추천 장소 반환

이 중 1~4는 Team B가 우선 구현하고, 5는 Team A가 보상 정책과 연결한다. 6은 Team B가 외부 연관 관광지 API와 연결한다.

### 5.3 API 문서화

- API 계약 변경 전 `agents_docs/07_api_specification.md` 또는 작업 이슈에 request/response를 먼저 작성한다.
- 프론트는 임시 mock 데이터가 필요할 경우 실제 API 응답 형태와 동일하게 만든다.
- 백엔드는 API가 준비되면 Swagger 또는 HTTP 예시를 검증 산출물에 남긴다.
- 식별자 이름은 `userId`, `spotId`, `stampId`, `potatoId`, `missionId`, `rewardId`, `couponId`를 우선 사용한다.
- 방문 인증 성공 이벤트 순서가 바뀌면 Team A와 Team B가 함께 랠리북, 감자, 미션, 보상 영향 범위를 확인한다.
- 에러 코드나 상태값을 추가하면 프론트의 로딩, 빈 상태, 에러 상태 표현까지 함께 확인한다.

## 6. Recommended Implementation Order

1. Team A: 인증 세션 안정화와 `GET /api/users/me` 구현
2. Team B: `GET /api/spots`, `GET /api/spots/{spotId}` 구현
3. Team B: 지도 마커와 스팟 상세 연결
4. Team B: `POST /api/visits/verify` 방문 인증 구현
5. Team A: 랠리북 진행률과 다음 보상 API 구현
6. Team B: 감자 도감과 희귀도 로직 구현
7. Team B: 점순이 미션 조회/완료 구현
8. Team A: 보상함과 QR 쿠폰 구현
9. 두 팀: 스탬프 획득 → 감자 획득 → 미션 → 보상 전체 루프 통합 테스트
