# AGENTS.md

이 문서는 이 저장소에서 Codex와 다른 코딩 에이전트가 우선 참고해야 하는 작업 지시서입니다. `README.md`, `SKILLS.md`, 하위 디렉터리의 `AGENTS.md`보다 먼저 전체 작업 습관을 정하고, 더 구체적인 하위 지시가 있으면 그 지시를 함께 따릅니다.

## 1. 기본 원칙

- 작업 전 `git status --short --branch`로 현재 브랜치와 변경사항을 확인한다.
- 기존 사용자 변경사항은 되돌리지 않는다.
- 요청 범위를 작게 해석하고, 한 번에 하나의 기능/버그/리팩터만 다룬다.
- 변경 전에는 관련 코드와 테스트를 먼저 읽고, 기존 패턴을 따른다.
- 불필요한 리팩터, 포맷 전체 변경, 메타데이터 변경은 피한다.
- 중요한 도메인 규칙, 순서 의존 로직, 예외 처리, 동시성/DB 제약처럼 다른 사람이 코드를 읽을 때 의도를 바로 파악하기 어려운 부분에는 반드시 짧은 주석을 추가한다.
- 주석은 "무엇을 하는가"보다 "왜 이 방식이어야 하는가"를 설명한다. 단순 getter/setter, 명백한 분기, 코드와 같은 말을 반복하는 주석은 피한다.
- 파일명, 변수명, 브랜치명, migration 명칭은 역할이 명확하게 드러나야 한다. `bootstrap`, `init`, `temp`, `misc`처럼 모호한 단어는 단독으로 쓰지 않는다.
- 임시 검증 파일, 해시 생성 파일, 크롤러 산출물은 의도적으로 요청된 경우에만 커밋한다.
- 운영 장애, 배포 문제, 인증/권한, 데이터 무결성, 테스트 실패처럼 포트폴리오에 활용 가능한 문제 해결 사례가 생기면 추후 생성 예정인 `docs/PORTFOLIO_PROBLEM_SOLVING_GUIDE.md`를 확인하고, 필요 시 `docs/portfolio/`에 기록한다.

### 로컬 문서 보호 규칙

- `.md` 문서는 사용자의 작업 기록과 기획 의도가 담긴 로컬 자산으로 보고, 원격 `main`에서 삭제되었더라도 로컬 삭제를 그대로 따라가지 않는다.
- `AGENTS.md`, `PLAN.md`, `DECISIONS.md`, `SKILLS.md`, `docs/**/*.md`, `instructions/**/*.md`, `README.md`를 삭제, 이동, 이름 변경, 대량 정리하려면 반드시 먼저 사용자에게 대상 파일과 이유를 설명하고 명시적 승인을 기다린다.
- `git pull`, `git switch`, `git restore`, stash 적용, merge/rebase 중 `.md` 파일 삭제가 발생할 가능성이 보이면 즉시 멈추고 사용자 확인을 받는다.
- 문서 복구나 보호를 위해 필요한 경우에는 삭제를 수용하지 말고 이전 커밋, reflog, stash에서 해당 `.md` 파일을 되살린다.

### Karpathy Guidelines 적용

- 구현 전에 모호한 요구사항, 가정, 선택지를 드러내고 필요하면 질문한다.
- 요청을 만족하는 최소 코드로 해결하며, 단일 사용처를 위한 과한 추상화나 추측성 확장은 만들지 않는다.
- 변경은 수술적으로 제한하고, 관련 없는 코드·주석·포맷은 개선 욕심으로 건드리지 않는다.
- 작업을 검증 가능한 목표로 바꾸고, 가까운 테스트나 빌드로 성공 기준을 확인할 때까지 반복한다.

## 2. 작은 작업 단위

작업은 다음 단위로 쪼갠다.

1. 컨텍스트 확인: 관련 파일, 테스트, 설정, 기존 이슈를 확인한다.
2. 최소 변경: 요청을 만족하는 가장 좁은 파일 집합만 수정한다.
3. 국소 검증: 변경한 모듈의 가장 가까운 테스트부터 실행한다.
4. 넓은 검증: 영향 범위가 크면 모듈 전체 테스트나 빌드를 실행한다.
5. 요약: 변경 파일, 검증 결과, 남은 리스크를 짧게 기록한다.
6. 커밋/푸시: 검증 통과 후 필요한 파일만 스테이징하고 작업 브랜치에 push한다.

### 중간 커밋과 push

- 작업 중에는 검증 가능한 작은 단위가 끝날 때마다 즉시 커밋하고 원격 브랜치에 push한다.
- 큰 기능 전환은 한 커밋에 몰아넣지 않는다. 예: 도메인 이름 변경, DB migration, API 계약 변경, 테스트 수정, 문서/README 수정, 성능 스크립트 수정은 가능하면 별도 커밋으로 나눈다.
- 한 커밋은 리뷰어가 5분 안에 의도를 파악할 수 있는 범위를 목표로 한다. 여러 책임이 섞였다고 느껴지면 커밋하기 전에 더 쪼갠다.
- 중간 커밋 전에는 해당 단위에 가장 가까운 테스트나 빌드를 실행하고, 실패하면 push하지 않는다.
- 사용자가 "중간중간 commit/push"를 요청한 작업에서는 최종 완료 전이라도 의미 있는 단위마다 반드시 commit과 push를 반복한다.

### 토큰/컨텍스트 절약 및 인계

- 작업이 길어질 것 같으면 기능 단위를 더 작게 쪼개고, 검증 가능한 최소 단위마다 커밋한 뒤 원격에 push한다.
- 각 커밋 전후로 현재 진행 상태, 완료된 항목, 다음에 이어서 할 일을 추후 생성 예정인 `PLAN.md`나 관련 문서에 짧게 남긴다.
- 컨텍스트가 부족해질 가능성이 있으면 새 작업을 시작하기보다 현재 작은 단위를 검증, 커밋, push하는 것을 우선한다.
- 이어받는 에이전트가 바로 재개할 수 있도록 미완료 리스크, 필요한 환경 변수, 실행 명령을 구체적으로 기록한다.

### 버전이 강제하는 규칙

에이전트가 반드시 지켜야 하는 핵심 규칙:

- **Flutter 3.x / Dart**: 프론트엔드는 Flutter 앱을 기준으로 한다. 상태 관리는 Riverpod, 라우팅은 GoRouter, 네트워크는 Dio를 우선 사용한다.
- **관리자 웹을 별도로 만들 경우**: 웹 프레임워크와 버전은 별도 이슈/PR에서 결정하고 문서에 명시한다. 현재 MVP 프론트엔드 기준은 Flutter이다.
- **Spring Boot 3.5.x / Java 21**: virtual threads(`spring.threads.virtual.enabled=true`) 사용 가능. JPA 어노테이션은 `jakarta.persistence.*`만 사용한다 (`javax.*` 금지).
- **메이저 업그레이드**(Spring Boot 4.x, Flutter 메이저 업그레이드 등)는 별도 PR로 진행하고 추후 생성 예정인 `DECISIONS.md`에 근거를 남긴다.

## 4. 검증 규칙

검증 명령의 단일 정답은 추후 생성 예정인 `TESTING_GUIDE.md`에 둔다. 이 섹션은 그 전까지 사용하는 요약이다.

### 이슈별 검증 산출물

#### 공통 산출물

- 모든 기능/버그/리팩터 작업은 진행 중인 Issue 번호 기준으로 `artifacts/validation/issue-<번호>/` 폴더를 만들고 검증 산출물을 남긴다.
- 각 Issue 검증 폴더에는 반드시 `VALIDATION.md`를 작성한다.
  - 작성 내용: 작업 목표, 진행 과정, 발생한 문제점, 해결 방법, 변경 파일 요약, 실행한 명령, 결과, 남은 리스크, 후속 작업.
  - 실패했던 시도도 숨기지 않고 기록한다. 예: 서버 실행 실패, Docker 미실행, migration 충돌, 브라우저 캡처 실패 등.
- 검증 캡처 파일명은 무엇을 검증했는지 알 수 있게 작성한다. 예: `swagger-letters-api.png`, `db-letters-row.png`, `k6-letter-summary.png`, `home-desktop-full.png`.
- 산출물은 사용자가 나중에 포트폴리오/문제 해결 기록으로 재사용할 수 있게 충분히 구체적으로 남긴다.
- 검증 산출물은 원칙적으로 로컬 기록이다. PR에 첨부하거나 GitHub에 올릴지는 사용자 요청 또는 AGENTS.md의 별도 지시가 있을 때만 진행한다.

#### Backend 산출물

백엔드 작업은 가능한 경우 다음 파일을 `artifacts/validation/issue-<번호>/`에 남긴다.

- `VALIDATION.md`: 백엔드 작업 목표, API/DB 변경 과정, 발생한 문제와 해결 과정, 실행한 테스트/빌드/서버 구동 명령, 결과, 남은 리스크를 기록한다.
- 테스트/빌드 산출물: Gradle test/build 결과 캡처 또는 핵심 로그를 저장한다. 실패 후 수정했다면 실패 로그와 통과 로그를 둘 다 남긴다.
- Swagger/OpenAPI 산출물: 변경된 endpoint, request schema, response schema, error code가 보이는 Swagger UI 또는 `/v3/api-docs` 확인 화면을 저장한다.
- DB 산출물: migration 적용 상태, 테이블/컬럼 구조, 실제 테스트 데이터 저장 여부를 확인한 화면 또는 쿼리 결과를 저장한다.
- API 호출 산출물: `curl`, Swagger, HTTP client 등으로 생성/조회/예외 응답을 확인한 결과 파일이나 캡처를 저장한다.
- 성능/관측성 산출물: k6, Grafana, Prometheus가 관련된 작업이면 k6 summary/report, Grafana dashboard, Prometheus query 결과 캡처를 저장한다.
- k6 부하 테스트를 실행한 경우 Grafana 대시보드 캡처에는 CPU Usage, Memory Usage, Request Duration, Throughput 그래프가 모두 포함되어야 한다.
- Grafana 캡처 후 `VALIDATION.md`에는 CPU, Memory, Request Duration, Throughput 관점의 분석과 병목/리스크를 기록한다.
- 제약 사항: Docker 미실행, 포트 충돌, 인증 실패 등으로 일부 산출물을 만들지 못하면 `VALIDATION.md`에 원인과 대체 검증을 기록한다.

#### Frontend 산출물

프론트엔드 작업은 가능한 경우 다음 파일을 `artifacts/validation/issue-<번호>/`에 남긴다.

- `VALIDATION.md`: 프론트 작업 목표, 참고한 디자인 가이드/레퍼런스, UI 결정, 발생한 문제와 해결 과정, 실행한 빌드/브라우저 검증, 남은 리스크를 기록한다.
- 풀스크린샷: 진행 중인 화면의 full-page screenshot을 저장한다. 데스크톱 우선 작업이라도 최소 1장의 데스크톱 full-page screenshot을 남긴다.
- 반응형 산출물: 모바일/반응형을 작업한 경우 모바일 full-page screenshot도 함께 저장한다.
- 상태별 산출물: 기본 상태, 로딩/빈 상태, 에러 상태, 모달/드롭다운 열림 상태처럼 중요한 UI 상태가 있으면 상태별로 저장한다.
- 빌드/정적 검사 산출물: `flutter analyze`, `flutter test`, `flutter build` 등 실행 결과의 핵심 로그를 `VALIDATION.md`에 기록한다.
- 사용자 검토 산출물: 사용자가 중간 검토를 요청했거나 화면 작업이 의미 있는 단위로 끝났다면 채팅에도 스크린샷을 보여준다.
- 레이아웃 품질 기록: 깨짐, 겹침, 잘림, 폰트 로딩, 이미지/아이콘 렌더링을 어떻게 확인했는지 `VALIDATION.md`에 남긴다.

### Backend

- 백엔드는 Java 21, Spring Boot 3.5.x, Gradle 단일 모듈 기반의 modular monolith 구조를 따른다.
- 백엔드 도메인 코드는 한 패키지에 모두 몰아넣지 않고 역할별 하위 패키지로 분리한다.
  - `api`: API endpoint, request/response DTO
  - `application`: 유스케이스, 트랜잭션, 도메인 조합 로직
  - `domain`: JPA Entity, enum, 값 객체, 도메인 정책, repository interface, 도메인 예외
  - `infrastructure`: DB 접근 구현체, QueryDSL, 외부 API, Redis, S3 연동
- Controller의 각 endpoint 메서드에는 해당 endpoint가 어떤 사용자 흐름과 비즈니스 작업을 처리하는지 설명하는 짧은 주석을 반드시 남긴다.
- 가능한 한 가장 좁은 테스트를 먼저 실행한다.
  - 백엔드 단위/통합 테스트: `cd backend && ./gradlew test`
  - 전체 백엔드 빌드: `cd backend && ./gradlew build`
  - Windows: `./gradlew` 대신 `.\gradlew.bat` 사용
- 포맷/정적 검사가 필요하면 Gradle에 정의된 Spotless/Check 태스크를 확인해 실행한다.
- DB 스키마 변경은 Flyway migration으로 관리하고, 엔티티/DTO/API 응답/테스트를 함께 갱신한다.

## 5. Git 규칙

- 운영 프로젝트이므로 `main` 직접 push는 금지한다. 긴급 장애 복구처럼 사용자가 명시적으로 허용한 경우에만 예외로 한다.
- 개발 작업 전 GitHub Issue를 먼저 작성한다. Issue 본문은 `.github/ISSUE_TEMPLATE/task-template.md` 또는 더 구체적인 템플릿을 따른다.
- 기본 작업 흐름은 `main`을 최신화한 뒤 `<type>/<issue-number>-<작업명>` 브랜치를 생성해 작업하고, 검증 후 원격 브랜치와 PR로 반영하는 것이다.
- 브랜치 접두어는 작업 목적에 맞게 `feat/`, `fix/`, `docs/`, `refactor/` 중 하나를 사용한다.
- 브랜치 이름에는 `bootstrap`, `codex`, `init`처럼 모호하거나 에이전트 식별을 드러내는 단어를 사용하지 않는다.
- 브랜치 예시는 `feat/12-user-session`, `docs/34-readme-workflow`처럼 Issue 번호를 포함한다.
- 작업 시작 전 `main`으로 전환하고 원격과 동기화한다. 원격 동기화가 필요하면 `git pull --rebase`를 고려하되, 충돌 가능성이 있으면 먼저 상태를 설명한다.
- 커밋은 원자적으로 만든다. 서로 독립적인 변경을 한 커밋에 섞지 않는다.
- 의미 있는 작업 단위가 끝날 때마다 중간 커밋을 남긴다. 예: 문서 정책 정비, 테스트 설정 추가, README 작성은 각각 분리한다.
- 스테이징 전 `git diff`와 `git status --short`를 확인한다.
- 이번 작업과 무관한 파일은 스테이징하지 않는다.
- 커밋 메시지는 한국어로 작성한다.
- 테스트나 빌드가 실패한 상태에서는 push하지 않는다. 실패를 명시하고 멈춘다.
- 검증이 통과하면 관련 파일만 커밋한 뒤 현재 작업 브랜치를 원격에 push한다.
- PR 본문은 `.github/pull_request_template.md`를 우선 사용하고, 연관 이슈, 변경 요약, 리뷰 중점사항, 검증 결과와 캡처 자료를 포함한다.
- PR에는 변경 성격에 맞는 Labels를 붙인다. 필요하면 `type:*`, `area:*`, `priority:*` 계열 라벨을 추가하되 기존 라벨 삭제는 사용자 승인 후 진행한다.
- PR 머지는 사용자 승인, 필수 CI 통과, 운영 영향 확인 후 진행한다. 에이전트가 머지 권한을 가지고 있어도 사용자의 명시적 지시 없이 merge, squash merge, rebase merge를 수행하지 않는다.
- GitHub에서 squash merge를 할 때 최종 커밋 제목은 자동 생성된 브랜치명/영어 제목을 그대로 쓰지 않고, 아래 커밋 메시지 형식에 맞춘 한국어 제목으로 수정한다.
- push 전 현재 브랜치가 `main`이 아닌지와 원격을 확인한다.

## 6. 커밋 메시지

형식은 변경 영역에 따라 나눈다. 프론트엔드와 백엔드는 접두사를 붙이고, 문서/설정/공통 작업은 접두사를 붙이지 않는다.

```text
[FE] <type>(<scope>): <한국어 요약> (#<issue-number>)
[BE] <type>(<scope>): <한국어 요약> (#<issue-number>)
<type>(<scope>): <한국어 요약> (#<issue-number>)
```

사용 가능한 type:

- `feat`: 기능 추가
- `fix`: 버그 수정
- `docs`: 문서 변경
- `test`: 테스트 추가/수정
- `refactor`: 동작 변경 없는 구조 개선
- `chore`: 빌드, 설정, 도구, 산출물 관리
- `style`: 포맷 또는 스타일만 변경

예시:

```text
[FE] feat(stamp): 랠리북 보상 카드 UI 구현 (#10)
[BE] feat(stamp): 방문 인증 API 구현 (#12)
docs(agent): Codex 협업 운영 문서 추가 (#14)
chore(github): 이슈 템플릿 정리 (#15)
```

- `[FE]`는 `frontend/` 중심 변경에만 사용한다.
- `[BE]`는 `backend/` 중심 변경에만 사용한다.
- 문서, GitHub 템플릿, 루트 설정, 공통 정책은 접두사 없이 작성한다.
- 프론트와 백엔드를 모두 크게 바꾸는 작업은 가능하면 커밋을 분리한다.
- `<scope>`는 `map`, `stamp`, `auth`, `coupon`, `agent`, `github`처럼 변경 영역을 짧고 명확하게 쓴다.

## 7. 제품 품질 기준

- 사용자가 실제로 수행하려는 흐름을 기준으로 구현한다.
- 실패 상태, 로딩 상태, 빈 상태, 중복 입력, 잘못된 입력을 고려한다.
- API 변경은 프론트엔드 타입, DTO, 테스트, 문서를 함께 맞춘다.
- 통계/승률/해시처럼 도메인 정확도가 중요한 로직은 단위 테스트를 우선 추가한다.
- 보안 관련 변경은 인증, 권한, 입력 검증, 비밀값 노출 여부를 함께 확인한다.
- 성능에 민감한 목록/이미지/통계 화면은 불필요한 전체 재계산과 대량 렌더링을 피한다.

## 8. 완료 보고

작업 완료 시 다음을 짧게 보고한다.

- 변경한 핵심 파일
- 실행한 테스트/빌드 명령과 결과
- 커밋/푸시 여부
- 남은 리스크나 후속 작업
